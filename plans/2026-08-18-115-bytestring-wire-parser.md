# #115 — wire parser `String` → strict `ByteString`

> **Status:** REVIEWED & REVISED 2026-08-18. The review pass verified every cited line number and claim against the codebase and found three defects, all fixed below: (1) D6's "five call sites" undercounted by ~25 — `decodeCheckInputFile` is also called from `scripts/bench.hs:272,279`, directly from `scripts/measure.hs:133,139,162`, from `scripts/gen-mutants.hs` (4 sites), and from nine test files (~20 sites), so a signature change was never a 15-line edit; (2) D6 is redesigned to mirror D5 — a `ByteString` primitive plus a retained `String` wrapper — which shrinks the diff back to the original estimate *and* eliminates R3 by construction; (3) T4's differential property was tautological once D5's wrapper became the implementation, and is replaced with a reference-parser differential. Read §2 D1–D4 and revised D6/T4 before writing code.

**Goal:** Replace the `String` (`[Char]`) S-expression reader in `src/Lara/Wire.hs:183-264` with one over strict `ByteString`, taking the `parse` row of `tables/performance.tex` from **581.2 µs** to the **330–430 µs** band, while leaving every accepted input, every rejected input, and every R14 error position character-for-character unchanged.

**Architecture:** `P` holds a strict `ByteString` and an O(1)-sliced cursor; `B.span`/`B.break` replace the walking-and-rebuilding `span`/cons accumulation. `SExpr` keeps `String` atoms (the 258 µs drop-in row of #115's prototype, not the 174 µs ceiling). The new primitives are `parseSExprBS :: ByteString -> Either ParseError SExpr` and `decodeCheckInputFileBS :: ByteString -> Either WireError CheckInput`; the existing `String` versions of both survive as thin wrappers (D5, D6). Only the two paths the goal actually depends on move to `B.readFile` + the `BS` primitive: `app/Main.hs` (the shipped CLI) and `scripts/bench.hs` (the harness that produces the `parse` row). Everything else — `Lara.Measure`, `scripts/measure.hs`, the two loaders, `scripts/gen-mutants.hs`, and all nine test files that call `decodeCheckInputFile` — stays on the `String` wrapper and still exercises the new parser through it.

**Tech stack:** Haskell/GHC 9.14.1, `bytestring` and `text` (both already direct dependencies, `lara.cabal:82,87`), hspec + QuickCheck (`test/WireSpec.hs`, `test/DifferentialSpec.hs`), `scripts/differential.sh` against the Lean 4.32.0 reference driver, `make bench`, `make measure`.

## Global constraints

- `src/Lara/Wire.hs` is inside the trusted base (~8600 lines) that the paper characterizes, with the compiled Lean semantics as its differential oracle. No change to accepted inputs, rejected inputs, R14 messages, R14 positions, or verdict bytes.
- **`ParseError` line/column stay code-point-based**, because the Lean driver counts code points (`lean/Lara/Driver.lean:164-175`, `PState.input : List Char`). See D1.
- `maxDepth = 10000` and its "R14, not stack overflow" contract (`Wire.hs:212-218`) are preserved exactly — `scripts/differential.sh` distinguishes exit 2 from exit 1 on that behaviour.
- No frozen byte changes: `corpus-units/`, `fixtures/`, `bundles/`, `examples/*.core.sexp`, `measurements/frozen/` byte-identical afterwards.
- `SExpr` does not change. `printSExpr`/`printAtom` do not change.
- `tables/performance.tex` is generated by `make bench`, never hand-edited.
- Conventional Commits; lands as its own PR, separate from #114 (already merged as `84fee43`).

## 1. Background

### Where the time goes

The parser state is a lazy list of boxed `Char`:

```haskell
data P = P { pInput :: String, pLine :: !Int, pCol :: !Int }   -- Wire.hs:184-188
```

Every character costs a cons cell and a pointer chase. `parseForm`'s bare-atom branch does `span isBareChar` and then `length tok` — two walks that rebuild the token. `parseQuoted` accumulates a reversed `[Char]` one cons at a time. `parseList` allocates a fresh `P` record per element. `step` pattern-matches the head to update the cursor, so the input is traversed through a lazy-list spine even for pure skipping.

Measured throughput on `corpus-units/fre/C01/unit.core.sexp` (16.8 KB): **~32 MB/s for lexing alone, ~12 MB/s end-to-end decode**. `aeson` over `ByteString` sustains several hundred MB/s on comparable inputs.

### The prototype measurement (from #115)

A `ByteString` parser implementing the identical grammar (bare atoms per `isBareChar`, quoted atoms with the `\" \\ \n` escape set, `;` comments, the `maxDepth` bound), asserted to produce an `SExpr` equal to `parseSExpr`'s on the real input. Median of 5 sections of 200 runs, `-O2`, same library build, same machine:

| | µs |
|---|---|
| current `parseSExpr` (`String`) | **537** |
| `ByteString` parser → `String` atoms | **258** |
| `ByteString` parser → `ByteString` atoms | **174** |

The win comes mostly from `B.span`/`B.break` returning O(1) slices where the `String` version walks and rebuilds. The 258 µs row is the honest drop-in number and the one this plan targets; the 174 µs row is the ceiling if `SExpr` later carries `ByteString`/`ShortByteString` atoms, recorded here and deliberately not taken (§6).

### State after #114

`84fee43` landed the sibling fix (`parseTag` linear scan → `Data.Map.Strict`). The committed table (`tables/performance.tex`, generated at `0aa97ef`, Apple M5 Pro / 64 GB / darwin/aarch64 / GHC 9.14.1 / Lean 4.32.0) now reads:

| row | median (µs) | worst (µs) |
|---|---|---|
| end-to-end | 784.8 | 864.9 |
| **parse** | **581.2** | 650.5 |
| check + render, pre-decoded | 203.5 | 223.5 |

`parse` fell 1317.0 → 581.2 µs and the parse : check ratio fell 6.6x → **2.86x**. Tag dispatch is now a minor term; what remains in the `parse` row is dominated by the lexer this issue replaces.

### Why it matters beyond the table

`src/evaluation.tex:77-79` (paper repo) claims decoding consumes "roughly seven eighths" of end-to-end time. That sentence was written against the 1317 µs row and is already stale at 581.2/784.8 ≈ 74%. #116 asks either to fix the decoder and restate the paragraph (option A) or to spend a sentence conceding the split is an engineering artifact (option B). #114 was the cheap half of option A; **this issue is the half that decides whether option A closes.** At the predicted band the ratio falls to ~1.7–2.1x, at which point "decoding dominates" is no longer the honest summary and the paragraph gets rewritten rather than qualified.

### Considered and rejected: a Rust frontend

Recorded here because it is the reflexive reaction to a slow parser, and because rejecting it is load-bearing for the paper's TCB claim.

1. **A Rust `.lara` → `.sexp` frontend would change nothing measured.** The benchmark feeds `unit.core.sexp` (`src/Lara/Measure.hs:132`) and times `decodeCheckInputFile` — the checker decoding an *already-lowered* core S-expression. A Rust frontend emits exactly that file; the Haskell decode still runs afterwards, unchanged. Surface `.lara` parsing and elaboration are not in `tables/performance.tex` at all.
2. **Rewriting the decoder itself in Rust puts an FFI boundary inside the TCB.** It breaks the "8600 lines of Haskell" characterization and breaks the byte-identical two-driver differential against Lean, for a win obtainable in-language — the 258 µs row above is 2.1x without leaving Haskell.

## 2. Design decisions

### D1 — columns count **code points**, not bytes

This is the decision the issue asks to make explicitly, and the answer is forced.

`lean/Lara/Driver.lean:164-175` holds `PState.input : List Char` and advances `col := p.col + 1` per `Char`, with `col := p.col + tok.length` for bare atoms — Lean `String.length` is in code points. The Haskell side currently agrees because `readFile` decodes UTF-8 into `Char`s before the parser sees anything. A byte-counting `ByteString` parser would silently disagree with the oracle on any error located after a multi-byte character **on the same line**.

This is not hypothetical. `fixtures/corpus/strict-cert-unicode-theory.sexp` carries `é` inside quoted atoms (`(theories "sha256:é")`, and again in the certifier and assurance forms), is generated deliberately by `scripts/gen-corpus.hs:25,657`, and is asserted in `test/DifferentialSpec.hs:186`.

**Implementation.** Bare atoms are ASCII by construction (`isBareChar` restricts to `0x21..0x7e`), so their byte length *is* their code-point length. Only quoted-atom payloads and `;` comments can carry multi-byte sequences. So the cursor advances by the count of **UTF-8 non-continuation bytes** in the consumed span:

```haskell
-- Bytes b with (b .&. 0xC0) /= 0x80 start a code point; continuation bytes do not.
-- (Data.ByteString.count takes a Word8, not a predicate, so this is a fold.)
cpLen :: ByteString -> Int
cpLen = B.foldl' (\n b -> if b .&. 0xC0 /= 0x80 then n + 1 else n) 0
```

For the all-ASCII spans that make up ~100% of the corpus this is a single `foldl'` over a slice with no branch misprediction of consequence, and for bare atoms it can be skipped entirely in favour of `B.length`. Document the invariant in the `P` Haddock: *`pCol` counts code points; the input is UTF-8; bare atoms are ASCII so byte length and code-point length coincide there.*

### D2 — quoted-atom payloads are UTF-8 decoded at the closing quote

`SExpr` keeps `String` atoms (issue scope), so `parseQuoted` accumulates bytes and decodes once at the close rather than per character. Escape processing (`\"`, `\\`, `\n`) happens on bytes — all three escapes are ASCII and cannot occur inside a multi-byte sequence, so byte-level escape scanning is safe by UTF-8's self-synchronizing property.

Use `Data.Text.Encoding.decodeUtf8'` (the `Either UnicodeException` form) plus `Data.Text.unpack`, not `decodeUtf8` (partial, throws pure exceptions from inside a `Either`-returning parser) and not `decodeUtf8Lenient` (silently substitutes U+FFFD, which would make malformed input *accepted* with mangled content — a fail-open change inside the TCB).

The common case — an atom with no escapes and no non-ASCII — should take a fast path that slices directly and avoids building an intermediate.

### D3 — `unexpected character` must still render the code point

`parseForm`'s error branch is `perr p ("unexpected character " ++ show c)`. `show 'é'` is `'\233'`. A byte-level parser reaching a non-bare byte must decode the **one code point** at the cursor and `show` that, or the message drifts from Lean's on exactly the inputs D1 exists to protect. Decode-one-code-point at the error position is off the hot path, so it can be as slow as it likes.

### D4 — invalid UTF-8 becomes a located R14 error; **this is a behaviour change and must be probed first**

Today `readFile` decodes under the locale encoding, so invalid UTF-8 raises an `IOException` that `app/Main.hs:194-196` (`readFileEither`) turns into an IO-level error, **not** an R14 codec rejection. After the switch to `B.readFile`, invalid bytes reach the parser.

The intended behaviour is a located `ParseError` ("invalid UTF-8 in string literal") → R14 → exit 2, which is strictly better: it fails closed, it is located, and it goes through the same channel as every other codec fault. But it is a boundary behaviour change and the Lean side must be checked, not assumed: Lean's `IO.FS.readFile` has its own answer for invalid UTF-8, and the two drivers must agree on *outcome class* (both exit 2) even if the message differs.

**T0 (below) is a probe, not an implementation step:** feed a hand-built invalid-UTF-8 `.sexp` to both drivers on `main` and record what each does. The decision is only final once that is in the plan's execution record. If Lean silently substitutes U+FFFD and accepts, the honest resolution is to reject on the Haskell side anyway and file the divergence as its own issue — but that must be a recorded choice, not a discovery during review.

### D5 — `parseSExpr :: String -> …` survives as a wrapper

Three call sites take `parseSExpr` and two of them are naturally byte-oriented, but one is not:

| site | holds | action |
|---|---|---|
| `src/Lara/Syntax.hs:1602` (`sexpLitP`) | a `String` slice scanned mid-`.lara`-parse | **keep the `String` wrapper** |
| `src/Lara/Mutate.hs:1021` (`codecMutantsForBase`) | file bytes as `String`, emits `printSExpr` output | leave on the wrapper (generator, not hot, and its output bytes are frozen) |
| `src/Lara/Measure.hs:318` (`policyBytes`) | the row's bytes | leave on the wrapper — `Lara.Measure` stays on `String` entirely (D6) |

So: `parseSExprBS` is the primitive; `parseSExpr = parseSExprBS . TE.encodeUtf8 . T.pack`. Both stay exported (`Wire.hs:117`). The wrapper's round-trip through UTF-8 is exact for any `String` that came from a UTF-8 decode, and D1's code-point columns make the two agree on error positions by construction — which is precisely the property T4's differential asserts.

### D6 — `decodeCheckInputFileBS` is the primitive; the `String` version survives as a wrapper, and only two callers move

**Revised at review.** The original design changed `decodeCheckInputFile`'s signature to `ByteString` and claimed "five call sites, ~15 lines". The real caller inventory is ~30 sites across 15 files:

- `app/Main.hs:99` (`checkSexp`)
- `scripts/bench.hs:170,181` (`benchUnit` — this produces the `parse` row) **and** `272,279` (`benchSweep`), fed by `readFile` at `168` and `265`
- `scripts/measure.hs:133,139,162` — **direct** calls in `timeHsCheck` (the timed codec-failure path) and `measureLean`'s agreement check, *in addition to* the indirect path `measure.hs:113,120` → `Lara.Measure.rowOutcome` (`Measure.hs:185`)
- `src/Lara/MechReview/Load.hs:22`, `src/Lara/ClaimSupport/Load.hs:51`
- `scripts/gen-mutants.hs:62,98,186,241` (generator; its output bytes are frozen under `fixtures/mutants/`)
- ~20 sites across nine test files (`MeasureSpec`, `MutationSpec`, `WireSpec`, `CliSpec`, `DifferentialSpec`, `MechReviewSpec`, `RuntimeSpec`, `AblationSpec`, `CheckSpec`), some on `String` values that never came from a file (`decodeCheckInputFile (printSExpr encoded)`, `decodeCheckInputFile "(unit)"`) — and `MeasureSpec`/`AblationSpec` additionally call `computeDeterministic`/`computeAblation` with `String` bytes, so moving `Lara.Measure` to `ByteString` ripples into them too.

A signature change is therefore a 15-file diff, most of it churn in test files that pin frozen behavior. The revised design mirrors D5 exactly:

```haskell
decodeCheckInputFileBS :: ByteString -> Either WireError CheckInput   -- the primitive
decodeCheckInputFile   :: String     -> Either WireError CheckInput   -- retained wrapper
decodeCheckInputFile = decodeCheckInputFileBS . TE.encodeUtf8 . T.pack
```

Both exported. Only the two paths the goal depends on move to `B.readFile` + the primitive:

| call site | reader change |
|---|---|
| `app/Main.hs:93-99` (`checkSexp`) | add `readFileBytesEither :: FilePath -> IO (Either IOException ByteString)` beside `readFileEither` (`app/Main.hs:194-196`) — the other two `readFileEither` sites (`Main.hs:122,130`) feed the `String`-based surface parser and must keep the `String` reader |
| `scripts/bench.hs` `benchUnit` (`168-181`) and `benchSweep` (`263-281`) | `readFile` → `B.readFile`; the `evaluate (length bytes)` forcing becomes `evaluate (B.length bytes)` (already forced — strict `ByteString` — but keep the `seq` shape for clarity) |

Everything else stays on the wrapper, deliberately:

- **`Lara.Measure` and `scripts/measure.hs` stay on `String`.** `computeDeterministic` computes `detTotalBytes = length bytes` (`Measure.hs:241`) on a `String`, so that field counts **code points** despite its name, and it is `report.tsv` column 12 — inside the freeze protocol's hashed projection. Leaving `Lara.Measure` untouched keeps that semantics identical *by construction* rather than by an "all-ASCII so it coincides" argument. The agreement and deterministic-metric machinery still exercises the new parser through the wrapper. (`measure.hs`'s `hs_check_ns` codec-row timing now pays the wrapper's `pack`/`encodeUtf8` conversion; that column is wall-clock, reported, and explicitly not frozen.)
- **`MechReview/Load` and `ClaimSupport/Load` stay on `String`.** Neither is in `tables/performance.tex`; moving them buys nothing and extends the D4 boundary change to paths the differential does not pin.
- **`gen-mutants.hs` and all test files compile unchanged.**

Consequence for D4: the invalid-UTF-8 behavior change applies exactly where the reader changes — the shipped CLI (`app/Main.hs`) and `bench.hs`. `scripts/differential.sh` invokes the CLI binaries, so T0's probe covers precisely the surface that changes.

### D7 — the parser shape

```haskell
data P = P { pInput :: {-# UNPACK #-} !ByteString, pLine :: !Int, pCol :: !Int }
```

- `skipSpace` uses `B.span (\b -> b `elem` [0x20,0x09,0x0a,0x0d])`-style bulk skipping with a newline count, rather than one `step` per character.
- The bare-atom branch is a single `B.span isBareByte`, with `B.length` as the column delta (ASCII by construction, D1).
- `isBareByte :: Word8 -> Bool` mirrors `isBareChar` exactly on `0x21..0x7e` minus `();"\\`; every byte `>= 0x80` is non-bare, which is the same answer `isBareChar` gives for any non-ASCII `Char`. Keep `isBareChar` — `printAtom` still uses it and is out of scope.
- `B.null` and `B.length` are O(1) on strict `ByteString`, so the "expected a single S-expression, found more input" end check stays O(1).
- `maxDepth` threading is unchanged: same `Int` depth parameter, same guard, same message.

### Considered and deferred

- **`SExpr` with `ByteString`/`ShortByteString` atoms.** The 174 µs row. Out of scope by the issue's own statement: it touches every consumer of `SExpr` across the codebase and the Lean mirror, for a further ~85 µs on the prototype. Revisit only if #116 still is not closable after this lands.
- **Rewriting `printSExpr`/`printAtom` over `Builder`.** A full `encodeCheckInput` + `printSExpr` round-trip measured ~1660 µs on `fre/C01`, so this is a real number — but the verdicts the CLI actually prints are far smaller than a `CheckInput`, and the `parse` row does not include printing. Separate change, separate issue.
- **A `bytestring` `Builder` or `attoparsec` rewrite.** Adds a dependency (or a combinator layer) inside the TCB for a hand-written 80-line grammar. The prototype gets 2.1x with `B.span`/`B.break` alone.

The differential is the oracle. A lexer regression on real inputs surfaces there as a decode divergence, not as numeric drift — which is exactly why the perf run is gated behind it.

### 4.2 Performance — the falsifiable part

Protocol: `make bench` on the **same machine as the committed table** (Apple M5 Pro, 64 GB, darwin/aarch64, GHC 9.14.1, Lean 4.32.0 — `measurements/bench.json:environment`), same GHC flags, machine otherwise idle. Run once on this branch **before** the parser change to get a same-session baseline, and once after; compare those two, not the `0aa97ef` numbers.

**Prediction, recorded before measuring.** The prototype's 537 → 258 µs was measured on `fre/C01`, whose marginal parse was 1892 µs against a published median of 1317 µs at that time — a unit-to-median scaling factor of ≈ 0.70. Applying it: the lexer accounts for ≈ 537 × 0.70 ≈ 376 µs of the current 581.2 µs `parse` row, and the `ByteString` version should cost ≈ 258 × 0.70 ≈ 181 µs. That is a saving of ≈ 195 µs, with the D1 code-point counting a small tax the prototype did not pay.

- median `parse`: 581.2 µs → **330–430 µs** (a 26–43% drop)
- median end-to-end: 784.8 µs → **530–630 µs**
- `check + render`: 203.5 µs → **unchanged** (within noise; nothing on that path moved)
- parse : check+render ratio: 2.86x → **1.6–2.1x**

**What counts as a failed hypothesis.** If the median `parse` drop is under 12%, do **not** commit the regenerated table. The likely causes, in order: the code-point counting in D1 is costing more than modelled (test by temporarily substituting `B.length` and re-running — a diagnostic only, never committed); the quoted-atom decode in D2 is not hitting its fast path; or the remaining `parse` cost is structural decoding rather than lexing, in which case the whole premise of #115 is wrong and that finding belongs in #116. Profile (`-prof -fprof-auto` on one corpus unit, or the `+RTS -s` allocation delta) before landing anything. If `check + render` moves more than a few percent in either direction, the run is noisy or the build differs — re-run before drawing conclusions.

**What this change settles for #116.** At the predicted band, `parse` is 1.6–2.1x `check + render` rather than 6.6x as the paper's sentence assumes. "Decoding dominates … roughly seven eighths" becomes false, and the honest end state for #116 is to rewrite the paragraph around measured numbers (option A) rather than qualify it (option B). At the pessimistic end (430 µs, 2.1x) that is still the right call; only a failed hypothesis leaves option B on the table.

### 4.3 Optional confirmation

If the end-to-end delta lands outside the predicted band, reproduce the prototype's isolated measurement before investigating further: time `parseSExprBS` and `parseSExpr` over `corpus-units/fre/C01/unit.core.sexp` in a loop seeded by an `IORef` (so GHC cannot CSE it), median of 5 × 200 runs, and assert the two produce equal `SExpr`s in the same harness. That separates the lexer change from everything else `make bench` folds together.

## 5. Risks and rollback

- **R1 — column semantics drift (D1).** Byte columns would diverge from Lean on any error after a multi-byte character. Mitigated by D1's code-point counting, T5's targeted cases, and the unicode-fixture row in §4.1. This is the single most likely way to ship a silent divergence.
- **R2 — invalid UTF-8 changes outcome class (D4).** Mitigated by T0 probing both drivers on `main` before any code is written, and by rejecting rather than substituting.
- **R3 — frozen measurement semantics flip.** Largely **dissolved by the revised D6**: `Lara.Measure` and `scripts/measure.hs` are not touched, so `detTotalBytes = length bytes` (`Measure.hs:241`) keeps its current code-point semantics by construction rather than by an all-ASCII coincidence argument. The §4.1 SHA-256 anchors (`docs/m5-freeze-checklist.md:186-194`) stay as gates anyway — they now also detect any *indirect* drift through the shared wrapper — and a mismatch still blocks the PR rather than getting re-frozen. Re-freezing to accommodate a decoder refactor would be the wrong resolution — the freeze exists so a perf change cannot quietly move an evaluation number.
- **R4 — escape handling on bytes.** Mitigated by UTF-8 self-synchronization (`"`, `\`, `n` are ASCII and cannot appear inside a multi-byte sequence), plus T5's escape cases.
- **R5 — the depth bound stops being the thing that fires.** A `ByteString` parser with different strictness could stack-overflow before hitting `maxDepth`, which `scripts/differential.sh` would misread as exit 1. Mitigated by the explicit T5 depth case and the §4.1 row.
- **R6 — regenerating the table on a different machine.** Every row moves and the comparison is meaningless. Check `measurements/bench.json:environment` before running.
- **Rollback:** one PR, one parser plus two mechanical call-site edits. `git revert` restores the `String` reader and the previous table. Because both `String` signatures are retained as wrappers (D5, D6), a revert of `Wire.hs` alone is not sufficient — revert the whole commit.

## 5b. Execution record

### T0 — the invalid-UTF-8 probe (D4), run on `main`'s code before any edit

Probe input: `fixtures/corpus/strict-cert-unicode-theory.sexp` with the `é`
(`0xC3 0xA9`) inside `(theories "sha256:é")` replaced by the single byte `0xFF`.

| driver | exit | stdout | stderr |
|---|---|---|---|
| Haskell CLI (`lara check`) | **2** | empty | `lara: cannot read …: hGetContents: invalid argument (cannot decode byte sequence starting from 255)` |
| Lean driver (`lara-driver`) | **2** | empty | `lara-driver: cannot read …` |

Both drivers already **fail closed at read time** with the same outcome class
(exit 2, empty stdout); neither substitutes U+FFFD and accepts. `scripts/differential.sh`
compares stdout and exit code, and compares stderr only for the two pinned
rejection classes (`reject-preflight-*`, `reject-r9`) and the generated mutants
— none of which is an invalid-UTF-8 input.

**D4 frozen as designed.** After the switch to `B.readFile`, the Haskell side
still exits 2 with empty stdout, but the fault now arrives as a located R14
codec error through the same channel as every other codec fault rather than as
an IO-level read failure. That is strictly better and changes no compared
byte. `test/WireSpec.hs`'s `prop_invalidUtf8Rejected` pins it, including that
it fails closed rather than substituting.

### T8 — the measured result

**The machine was not idle.** Load average sat at 3.0–4.4 for the whole session
(WindowServer, Activity Monitor, WeChat), and every row — including rows this
change cannot touch — runs ≈ 1.4x above the committed `0aa97ef` table. The
`0aa97ef` numbers are therefore **not** a valid comparator, exactly as §4.2
anticipated. What follows is the same-session pair the protocol calls for: both
runs at `git_rev 1b2d245`, same binaries, same 120 s settle before the timed
work, the rebuild deliberately outside the timed command.

| row | baseline (String parser) | after (ByteString parser) | delta |
|---|---|---|---|
| end-to-end (µs) | 1115.5 | 747.2 | **−33.0%** |
| **parse (µs)** | **813.0** | **442.8** | **−45.5%** |
| check + render, pre-decoded (µs) | 300.0 | 309.6 | +3.2% |
| 564-record harness sweep (ms) | 545.6 | 278.4 | −49.0% |

- The parse row fell **45.5%**, above the predicted 26–43% band and far above
  the 12% failed-hypothesis floor. The prediction under-modelled the win; the
  D1 code-point tax is smaller than budgeted because `B.elemIndexEnd`/`B.count`
  do the line arithmetic in bulk and bare atoms skip `cpLen` entirely.
- `check + render` moved **+3.2%**, inside §4.2's "within noise; nothing on
  that path moved" tolerance — the sanity check that the delta is the lexer and
  not the build.
- parse : check+render fell **2.71x → 1.43x**.
- A first, unsettled baseline (taken immediately after a full GHC rebuild) read
  1136.9 / 834.8 / 305.4; the settled baseline read 1115.5 / 813.0 / 300.0.
  The two agree within 3%, so the ≈1.4x inflation is ambient machine load, not
  a thermal artifact of the rebuild.

**`tables/performance.tex` is deliberately NOT regenerated in this PR.** Under
this load the untouched `check + render` row would move 203.5 → 309.6 µs, a 52%
apparent regression that is purely machine state. Committing that would move an
evaluation number for a reason unrelated to the change — the thing the freeze
protocol exists to prevent. The table must be regenerated by one `make bench`
on an idle machine; the code change is independent of it and lands now.

**What this settles for #116.** At 1.43x, "decoding dominates … roughly seven
eighths" is false by a wide margin — parse is now ≈ 59% of end-to-end, not 87%.
#116 closes as **option A**: rewrite the paragraph around measured numbers.
The qualifying sentence (option B) is off the table. The rewrite is gated on
the idle-machine table, not on this PR.

## 6. Out of scope

- Changing `SExpr` to carry `ByteString`/`ShortByteString` atoms (the 174 µs ceiling).
- Rewriting `printSExpr`/`printAtom`, or the `encodeCheckInput` round-trip cost.
- Any change to the wire grammar, the tag vocabulary, or any spelling.
- Editing `src/evaluation.tex` — that is #116, and it is gated on this PR's measured numbers.
- `Lara.Syntax`'s own `.lara` surface parser (a separate `String` parser; surface parsing is not in `tables/performance.tex`).
