# Releasing Lara

How a Lara release is cut and how it reaches Homebrew.

## What a release ships

A release is a `vX.Y.Z` tag on `main` plus its GitHub release. The release
workflow (`.github/workflows/release.yml`) attaches one tarball per platform:

| Target | Runner | Asset |
| --- | --- | --- |
| macOS Apple Silicon | `macos-14` | `lara-aarch64-apple-darwin.tar.xz` |
| Linux x86_64 | `ubuntu-22.04` | `lara-x86_64-unknown-linux-gnu.tar.xz` |

Each tarball holds one top-level directory with the stripped `lara` binary,
`LICENSE`, `README.md`, and `examples/E1/` (the example `brew test` checks).
Next to each tarball is a `.sha256` file. The binaries are built with the same
GHC the required `Haskell` workflow uses (9.6). The workflow's "Show dynamic
libraries" step prints each build's linkage. The macOS binary links only
`/usr/lib` system libraries. The Linux binary links glibc and `libgmp.so.10`
dynamically. It needs glibc 2.35 or newer, because it is built on Ubuntu 22.04,
and it needs a system GMP, which ships with any distribution that has GCC.

These two targets match the ones the tap already serves for `ara`. On any other
platform, build from source (`cabal install exe:lara`).

## Versioning

The version is `0.MINOR.PATCH` (`lara.cabal` appends a fourth `.0`).

- A merge that adds a new semantics on a new logical framework bumps the
  minor version and resets the patch: the Belief Hoare Logic (`0.2.0`) and the
  research-process semantics (`0.3.0`).
- Every other merged PR bumps the patch, whatever its type (`docs`, `ci`,
  `theory`, `feat`). Commits pushed to `main` without a PR do not bump.

The PR carries its own bump: it edits `version` in `lara.cabal` and
`CITATION.cff` (with `date-released`), and the squash commit is tagged with
that version after merge.

## Cutting a release

1. Bump `version` in `lara.cabal` and `CITATION.cff`, merge to `main`.
2. Tag and push: `git tag vX.Y.Z && git push origin vX.Y.Z`. The workflow
   builds both targets, runs the smoke test (`lara check
   examples/E1/example.lara` must accept), and uploads the assets. It creates
   the GitHub release if one does not exist.
3. Update `Formula/lara.rb` in
   [ARA-Labs/homebrew-tap](https://github.com/ARA-Labs/homebrew-tap): set
   `version`, the two `url`s, and the two `sha256`s from the uploaded
   `.sha256` files. Then run `brew install ARA-Labs/tap/lara && brew test lara`.

To rebuild the assets for an existing tag, run the workflow by hand:
`gh workflow run release.yml -f tag=vX.Y.Z`. The upload uses
`--clobber`, so a rebuild changes the checksums, and the formula must be
updated to match.

## Why the formula is hand-updated

The tap's `ara` formula is generated by cargo-dist. Lara is a cabal project and
has no equivalent generator. Pushing to the tap from this repository's workflow
would need a cross-repository token, and the formula changes in only three
fields per release. Updating it by hand keeps that token out of this repository.

## v0.3: research-process semantics

[`theory-process.md`](theory-process.md)): when a record that omits part of
what happened still entitles a claim. The patch releases after it add the
inquiry contracts, wrapper, native door and evaluations, and further process
